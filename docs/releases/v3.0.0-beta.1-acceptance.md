Native packaging tests execute packaged applications on CI runners, but do
**not** prove that downloaded installers register correctly with the OS, that
upgrades from v2.2.3 preserve preferences, or that real machines accept platform
security prompts. Linux distro tests run under Xvfb in containers, not a real
user's desktop. Do not mark a pending column as passed based on CI.

AMR, APE and MPC input fixtures remain documented conversion-matrix coverage
gaps. An unavailable encoder or an absent track/fixture is not evidence that all
possible input/output pairs work. Record any test that unexpectedly fails for an
**advertised, supported** conversion as a defect, with fixture and FFmpeg
diagnostic evidence.

## Physical-machine acceptance checklist (still required)

Run the applicable rows **on actual supported devices**, not just in CI. Where
physical ARM64 Windows/Linux hardware is unavailable, document that explicitly,
keep the row pending and decide release support accordingly.

For each device, capture: OS/build, CPU architecture, downloaded asset name,
SHA-256, installed version, tester/date, screenshot or console log, and result.
Link this evidence back to [#62].

1. **Download integrity.** Download the matching OS/architecture build and
   `SHA256SUMS` from the [beta release]. Verify the downloaded file's digest
   against its **exact filename** in `SHA256SUMS`. Do not bypass a mismatch.
2. **Clean install.** Install the relevant native installer/package or extract
   the portable distribution. Verify the application starts from the desktop
   launcher/Start menu/Finder as applicable, not solely from a CI build path.
3. **Convert actual media.** Exercise one valid small video, audio and image
   input; check output plays/opens, file dimensions/duration where relevant,
   progress, error handling, cancellation and retry.
4. **Preferences.** Change theme, language, codec/quality and save destination
   where supported; quit, relaunch, and verify expected persistence.
5. **Upgrade from stable.** In a disposable user profile/VM, install published
   v2.2.3, save sample preferences, then install the beta as an upgrade. Verify
   whether both apps coexist, whether settings persist and whether the correct
   executable and shortcuts launch. **Report behavior; do not assume old
   preferences migrate.** Never erase the original profile during testing.
6. **Uninstall/reinstall.** Verify OS registration, uninstall entry/desktop
   icon, shortcut cleanup and app-data treatment. Capture whether a reinstall
   loses or correctly retains supported preferences.
7. **System trust checks.** Record macOS Gatekeeper/signing/notarization status
   and Windows Authenticode/SmartScreen behavior **as observed**. The current
   beta is unsigned and unnotarized, so trust warnings are expected; the test
   does not override the platform's security decisions.
8. **Linux integration.** Verify actual DEB/RPM desktop entries, application
   icon, MIME associations if declared, permissions and startup on X11 and
   Wayland where available; also test portable archive launch.
9. **Regression and logs.** Confirm bundled FFmpeg runs from the installed app
   without missing-module errors, especially the historical Windows installer
   failure ([#44]) and macOS damaged-app report ([#49]).
10. **Evidence and signoff.** Record pass/fail/blocked for each applicable
    target. File reproducible bugs rather than counting warnings as passing
    functional tests. Retest failures after fixes.

### Optional command-line checksum examples

Run these in the directory containing the downloaded asset and `SHA256SUMS`,
substituting the **exact published filename** for `ASSET_NAME`.

- Linux: `grep -F '  ASSET_NAME' SHA256SUMS | sha256sum -c -`
- macOS: `grep -F '  ASSET_NAME' SHA256SUMS | shasum -a 256 -c -`
- Windows PowerShell: `(Get-FileHash -Algorithm SHA256 .\ASSET_NAME).Hash`;
  compare with the full 64-character hex digest on its `SHA256SUMS` row.

The commands assume a trusted checksum manifest from the same release, exact
file matching, and a case-insensitive hex comparison. Check that the selected
manifest row **exists** before treating output as verified.

## Signing and publishing policy

- The unsigned exception is limited to **exactly** `3.0.0-beta.1` by
  `releaseRequiresSigning` in `scripts/release-policy.mjs`. The policy tests
  reject unsigned builds of any later beta or stable version.
- **macOS signed releases:** valid Developer ID distribution certificate
  (`APPLE_CERTIFICATE_BASE64`, `APPLE_CERTIFICATE_PASSWORD`, `APPLE_IDENTITY`),
  Apple ID/app-specific password and team ID (`APPLE_ID`,
  `APPLE_APP_SPECIFIC_PASSWORD`, `APPLE_TEAM_ID`). Inspect actual Gatekeeper and
  notarization results before publishing.
- **Windows signed releases:** valid Authenticode PFX
  (`WINDOWS_CERTIFICATE_BASE64`, `WINDOWS_CERTIFICATE_PASSWORD`). Confirm the
  expected certificate thumbprint, actual signature trust on a Windows machine
  and installer publisher identity.
- **GitHub governance:** enforce tag restrictions, protected release environment
  and required reviewers/checks; limit access to repository signing secrets.
  Native signing jobs use repository secrets before the publish environment job,
  so publish approval alone is **not** equivalent to protecting signing
  credentials.
- **Release pipeline:** signed versions must fail closed when credentials or
  signature checks are absent; native receipt/version/commit/digests and Linux
  distro gates must pass before publish. No overwrite of published assets or
  reuse of the existing beta tag.
- **Linux:** packages do not pass the macOS/Windows code-signing verification
  path; validate their checksum, integration and any package-signing policy
  separately.

**No further unsigned release is authorized by this dossier.** The v3 beta's
approval is a one-version exception, not a change of default signing policy.
